# P1 设计：回放回归器与冠军指针

上级文档：[团队模式架构重审-2026-10-21.md](团队模式架构重审-2026-10-21.md) §3.3、§3.4、§6。
状态：已实现（2026-10-21）。拍板结果：用例库放 userData；退役由制作人决定（`regression_retire`，用户开团队模式即撒手不管）；P1 只在 `team_deliver` 和 `regression_run` 时跑回归。

## 0. P1 要交付的两件事

1. **回放回归器**：把「这一串输入打下去，游戏应该变成这样」存成一条可重跑的用例。盒子能随时把全部用例跑一遍、判出过或不过，全程不花 LLM token。只要有一条用例在验收时被锁定，后面谁都删不掉、也改不动。
2. **冠军指针**：盒子单独握着一个指针，指向「当前最好的可交付版本」。只有通过全部锁定用例、并且通过独立验收的快照，才能成为冠军。模型改不了这个指针。任何时候停工，交出去的都是冠军。

P1 只接进现有的团队模式（`team_deliver`）。单写者模式（P2）和成对比较裁判（P3）直接复用这两块。

## 2. 回放回归器

### 2.1 用例格式

```jsonc
// <userData>/regression/<工程键>/cases/c0007.json
{
  "id": "c0007",
  "title": "首房：起跳冲刺过针眼，到达出口",
  "scene": "res://levels/ch01_01.tscn",     // 空 = 主场景
  "seconds": 6,
  "seed": 1,                                  // 全局随机种子
  "inputs": [{ "action": "jump", "at": 0.5, "hold": 0.2 }, { "action": "dash", "at": 0.8 }],
  "watch": ["Player:global_position:x", "GameState:room_id", "Player:is_on_floor()"],
  "asserts": [
    { "expr": "GameState:room_id", "op": "==", "value": "ch01_02", "when": "ever" },
    { "expr": "Player:global_position:x", "op": ">=", "value": 1180, "when": "final", "tol": 2 }
  ],
  "status": "locked",                         // candidate | locked | flaky | retired
  "origin": { "by": "验收员", "at": 1792459000000, "snapshot": "a1b2c3d" },
  "lockedAt": 1792459100000
}
```

- **`when` 四种**：`final`（最后一次采样）、`at: <秒>`（离这个时刻最近的一次采样）、`ever`（任意一次采样满足）、`always`（每次采样都满足）。
- **`op`**：`== != < <= > >=`，数值比较允许 `tol`（容差）。值统一按 `var_to_str` 的字符串比；能解析成数的按数比，Vector2/3 支持 `:x`、`:y` 这种分量写法（运行器已经支持）。
- **每条用例都隐含三条断言**：跑到了 `GDBOX_END`（没崩、没卡死、没超时）；运行中没有脚本或引擎报错；没有出现 `unknown input action`（InputMap 被改名会被当场抓到）。

### 2.2 判定放在 TS 里，运行器只负责采数

`gdbox_run.gd` 已经会打印 `GDBOX_WATCH {t, v}`。断言在 TS 侧对原始采样行求值，不用 `summarizeWatch` 去重后的表。这样做的好处：
- 判定逻辑能单测，不用起 Godot；
- 运行器保持「只观察、不判断」，`godot_run` 和回放共用同一个运行器。

新文件 `core/regression/assert.ts`：给它采样序列和断言，返回每条断言是否通过，以及实际值是多少（出问题时报给模型看）。

### 2.3 运行器的三处小扩展（`gdbox_run.gd`）

1. **固定随机种子**：配置里带了 `seed`，就在实例化场景之前调用 `seed(seed)`。工程自己调用 `randomize()` 的话，种子会被冲掉，这种情况交给 §2.5 的「跑两遍比对」去抓。
2. **物理确定性**：设 `Engine.physics_jitter_fix = 0`。配合已有的 `--fixed-fps 60`，物理步长固定。
3. **按帧采样**：采样间隔允许精确到 1 帧（现在最小是 0.016 秒，四舍五入后可能是 0 或 1 帧）。断言用的 `ever`/`always` 需要逐帧数据。

`godot_run` 工具本身不变，扩展的部分只在回放时启用。

### 2.4 用例从哪来

| 来源 | 怎么进 | 初始状态 |
|---|---|---|
| 干活的 agent 证明了某个行为 | 新工具 `regression_add`：参数就是一次 `godot_run` 的参数再加上 `asserts` 和 `title` | `candidate` |
| 验收员 | 验收员提示词加一条：PASS 必须附至少一条覆盖「开始 → 胜/负 → 重来」完整循环的用例，用 `regression_add` 提交 | `candidate`，验收通过时直接锁定 |
| 用户 | P1 不做录制界面，只能删、能看 | — |

**入库门槛**（`regression_add` 的执行过程，由盒子完成）：
1. 在当前工程上把这条用例**连跑两遍**。
2. 两遍都通过，并且断言涉及的数值两遍一致（在容差内），才写进库，状态 `candidate`。
3. 两遍不一致，标 `flaky` 并告诉 agent 原因（最常见的是 `randomize()`，或依赖了真实时间），不进门禁。
4. 第一遍就没通过：拒收，把失败的断言和实际值回给 agent。用例必须在提交时就是对的。

### 2.5 锁定与只增不减

- **锁定只在冠军晋升时发生**：晋升成功时，所有在这个快照上通过的 `candidate` 一起转为 `locked`。
- **锁定的用例模型删不掉、改不了**：用例库在 userData 的写保护目录里，路径类工具写不进去；模型手里也没有删除用例的工具。
- **只有用户能把用例标成 `retired`**（在界面上操作，记下是谁、什么时候、为什么）。真要改玩法时，用户拍板退役旧用例。
- 命令和脚本类工具（shell）理论上能绕过路径保护，这一层跟现在一样靠审批门兜底（见 `pathBoundary.ts` 文件头）。另外每次读取用例库时会核对一份内容指纹清单，被改过就当场报给用户。

### 2.6 跑回归

新文件 `core/regression/runner.ts`：

```ts
runRegression(projectDir, cases, { signal, onProgress }): Promise<RegressionReport>
// RegressionReport = { treeId, results: Array<{ id, pass, failures[], ms }>, passed, failed }
```

- **串行跑**：和 `godot_run` 同一把串行锁，两个 Godot 同时导入会互相踩 `.godot/` 缓存。
- **缓存**：工程内容用快照仓库 `git add -A && git write-tree` 得到的 tree id 表示。结果按「tree id + 用例内容哈希」缓存在 `<userData>/regression/<工程键>/results.json`。工程没变就不重跑。这就是上级文档 §3.4 的「证据缓存」，治的正是 102 件重复验证。
- **耗时**：每条 5–20 秒墙钟，30 条大约 3–8 分钟，0 token。
- **对 agent 暴露一个工具 `regression_run`**：可以跑全部，也可以按 id 跑几条。返回值只有一行汇总加失败项（每项附实际值），不带完整采样表，免得撑大调用方的上下文。

## 3. 冠军指针

### 3.1 记录放在哪

```jsonc
// <userData>/regression/<工程键>/champion.json  （写保护）
{
  "commit": "<完整 40 位提交号>",           // 快照仓库里的提交
  "snapshot": "a1b2c3d",
  "treeId": "<tree id>",
  "promotedAt": 1792459100000,
  "evidence": {
    "check": "0 errors",
    "cases": { "locked": 12, "passed": 12 },
    "acceptance": { "verdict": "pass", "reason": "…", "by": "acceptor" }
  },
  "history": [ /* 历届冠军，只追加 */ ]
}
```

- 快照仓库里同时写一个 `refs/gdbox/champion`，作用只是防止这个提交被 git 回收。**以 userData 里那份为准**：提交号由内容决定、伪造不了，模型就算用 shell 改了 ref，也改不动 userData 里的记录。
- 快照的排除名单不用改：用例库和冠军记录都不在工程里，回滚工程碰不到它们。

### 3.2 晋升规则（P1 版）

候选快照 S 晋升为冠军，必须**同时**满足：
1. `godot_check` 零错误；
2. 全部 `locked` 用例在 S 上通过；
3. 独立验收在 S 上给了 PASS，并且验收之后工程没有再改过（用 tree id 比对）；
4. 已经有冠军的话，S 通过的用例数 ≥ 冠军通过的数（`candidate` 和 `locked` 都算）。

第 4 条是 P1 的简化版「更好」。P3 会加上主观项的盲评成对比较（「S 比冠军好吗」），以及判据账本里「未满足项更少」。

### 3.3 接进 `team_deliver`

现在的流程是：制作人调 `team_deliver` → 验收员玩一遍 → PASS/FAIL。P1 改成：

1. **存快照**，记下 tree id。
2. **先过机器门**：跑 `godot_check` 和全部 `locked` 用例，有一条不过就直接返回 FAIL，附上失败的用例和实际值，**不请验收员**。这一步省掉的，正是这局反复出现的「还没跑通就叫人来验」。
3. 机器门过了，再请验收员（验收员会顺手提交循环用例，见 §2.4）。
4. PASS → 按 §3.2 判晋升。晋升成功：锁定用例，回话写明「冠军已更新为 a1b2c3d」。晋升失败（例如通过的用例数变少）：如实说明原因，冠军不变。
5. FAIL → 冠军不变，回话末尾附一句「当前可交付的冠军仍是 X（某时某刻）」。

### 3.4 交付和停工都以冠军为准

- 交付闸（`teamSession.ts`）判「过没过验收」，改看**冠军存不存在**、以及工作区和冠军是否一致。
- 一轮结束时（用户停下，或交付闸推满两次）工作区如果比冠军新、但还没通过：在对话里给用户一张卡片，写明「最近一版可交付的是冠军 a1b2c3d（时间、用例 12/12、验收理由）；当前工作区还没通过」，附两个按钮「恢复到冠军」「保留工作区」。恢复直接复用现有的 `snapshots.restore` 和宿主层关编辑器、回滚、重开那一串。
- `team_snapshot` 回滚到比冠军还早的快照仍然允许：冠军记录不受影响，随时能恢复回来。

## 7. 怎么验证 P1 本身

- **单测**：断言求值（四种 `when`、容差、分量）、两遍比对判 flaky、晋升四条规则、锁定之后删改被拒、tree id 缓存命中。
- **集成测**：新建一个最小 Godot 工程夹具（仓库里目前没有 `project.godot` 夹具，要新加；测试按本机有没有 Godot 决定跑不跑），走完录入 → 两遍入库 → 晋升 → 改坏一处 → 机器门拦下、没请验收员 → 修好 → 再晋升。
- **真机**：在《缝天旅人》24 房完整版上录三条用例（首房通关到下一房、死亡后复位、暂停后保持动量），各跑 10 遍，确认确定性。这一步最能暴露物理或随机数上的不确定，要先做。

## 8. 需要你拍板的三件事

1. **用例库放在哪**
   - 方案 a（推荐）：放在 userData，模型改不了，但跟着工程拷不走。用户可以导出。
   - 方案 b：放在工程的 `.gdbox/` 里，跟着工程走，但模型用文件工具就能删改，「只增不减」得另想办法保证。
2. **锁定用例的退役权**：只有用户能退役（推荐）；还是允许模型提退役申请、由用户在界面上批？
3. **什么时候自动跑回归**
   - P1 只在 `team_deliver` 和 `regression_run` 时跑（推荐，先把机制跑通）。
   - 还是每件活交回后，在后台自动跑一遍、把结果写进活的回话里？这样回退能更早发现，代价是墙钟时间，以及编辑器那一个席位更忙。

## 9. 端到端实测记录（2026-10-21）

dev 版、隔离 userData，`/team` 做单屏《接星星》（工程 `H:\GameJam\e2e-接星星-luna`），全员 GPT-6 Luna，共 1253 万 token（额度 1000 万，监控间隔过长超了约 250 万）。

**验证通过**
- 机器门每次交付都跑了：`godot_check` + 回放回归；工程没变的用例直接用缓存（「0 条新跑」）。
- 不稳定判定正确：游戏用 `RandomNumberGenerator.randomize()`，相关用例全部判为 flaky，没有混进门禁。

**发现并已修复**
1. 每单重开把旧消息的 `usage` 删掉，pi-ai 每次请求直接读 `usage.totalTokens`，队员一派活就崩。改为全零用量（`memberMemory.ts`）。
2. 回放共用一个 `user://` 目录，存档会在两遍、两条用例之间串。改为每遍一个全新目录（`run.ts` 的 `userDataRoot`）。
3. 判为不稳定后队员换写法重存了 4 次。现在回放器把种子放在 `Engine` 元数据 `gdbox_seed` 上，不稳定时直接指出工程里调 `randomize()` 的位置和改法。
4. 验收提示词写成「PASS 之前必须存一条用例」，验收员把它当通过条件，能玩的游戏连判三次 FAIL、没产生冠军。改为「用例是辅助，不是交付标准」。

**发现、未修**
- pi-ai 流式解析工具参数时，每个片段都把累积的整段参数重新解析一遍（`parseStreamingJson`，平方复杂度）。一次 10.7 万片段的超长工具调用把主进程占住 13 分钟，整个应用停摆。所有 provider 都有。
- 制作人花了 940 万 / 1253 万：168 次请求，上下文涨到 10 万，自己跑 `godot_run` 16 次。这是架构重审里「取消制作人」那一条的直接证据。

**还没验证到**：冠军晋升（验收一直 FAIL）、改坏被拦、面板「恢复到冠军」。修完第 4 条后需要再跑一局。
