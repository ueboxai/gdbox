# 团队模式架构重审（2026-10-21）

起因：《缝天旅人》一局 12.95 亿 token。四个视角独立做了推演，彼此看不到对方的结论：第一性原理、控制论、信息流与上下文经济学、唱反调（带业界证据）。本文是综合后的结论。预算方案（`团队预算与里程碑设计-2026-10-20.md`）就此作废：它只管什么时候停，解决不了问题。

## 1. 这局的钱是怎么没的（四方结论一致）

浪费是三个因子相乘，不是哪一项单独超标：

| 因子 | 倍数 | 根源 |
|---|---|---|
| 方向推倒（2/3 花在被扔掉的版本上） | 约 3 倍 | 最贵的决定（范围、美术路线）放到最后才验证，推倒重来又没有任何代价 |
| 上下文膨胀（每步 18 万，必要的只有 4–5 万） | 约 4 倍 | 状态放在常驻 agent 的脑子里；邮件和转述在每个人的上下文里反复被重读 |
| 冗余：LLM 只读验证 102 件、40 次重新上手、R1–R8 | 约 1.5 倍 | 验证靠 LLM 互相复读，没有一个机器裁判 |

有效部分约 0.7 亿 token，占 5–8%。还有一个反直觉的点：一封 300 字的邮件，真实成本是发件人整段上下文，大约 15–25 万 token。协调消息只占 0.05% 的体积，却花掉了 20–40% 的 token。

## 2. 根本错误（不是参数问题）

1. **「AI 工作室」这个隐喻是错的。** 人类分工是为了绕开人的瓶颈：一个人学不全、一天只有 8 小时、知识传递很贵。LLM 正好相反：一个模型什么都会，复制几乎零成本，但每次交接都会丢上下文。照搬人类组织，就是为一个不存在的瓶颈付了真实的代价。业界证据也是同一个结论：
   - Anthropic：按上下文边界拆分任务，不按工种拆；多 agent 适合可并行的广度任务，编码任务能并行的部分少。
   - Cognition：只能有一个写入者，多 agent 只用来帮着想。
   - Google/MIT 测了 180 种配置：顺序约束类任务上，多 agent 一律下降 39–70%。
   - 我们的设计稿自己就引用了「按上下文拆」，实现却按工种拆。
2. **工作单元选成了「人」，而不是「任务」。** 状态放在常驻队员的记忆里：会过期，没核实过，辞退就丢了。队员最常用的工具还是 `read_local_file`，说明记忆的钱付了，重新读文件的钱也付了。
3. **没有机器裁判。** 中间验证全靠 LLM。LLM 打分的噪声（σ 约 0.5–1）比每轮的改进（约 0.2）还大，R1–R8 基本是在追噪声；要分辨出这么小的改进，需要约 50 次独立采样。
4. **进度不单调。** 盒子手里没有一个只进不退的状态，推倒重来对控制器来说完全免费。唯一的停机条件是 PASS，而 PASS 不一定够得着。所以用户才会说「停下来就白花了」，这句话是对的。
5. **「盒子不管脑子」划错了界线。** 题材、玩法、风格交给模型，这一条是对的。但组织拓扑、裁判、成本规律不是「脑子」，是环境：
   - 组织拓扑（谁持有什么状态、信息怎么流）决定了成本是哪个数量级。
   - 裁判（评分标准）就是目标函数本身。
   - 成本规律：先用最便宜的方式验证最贵的决定；机器能证明的不让 LLM 复读；不收敛就换方法。

## 3. 新架构

### 3.1 一个写入者，加用完即弃的工人
- **主建造者**：一个能动手的 agent，负责核心代码、整合，以及决定先做什么。没有只读的「制作人」夹在中间转话。上下文不靠越积越长：每次从盘上的状态重建，上限 6–8 万。
- **一次性工人**：只用于接口已经冻结、完成条件机器能判、不需要和别人说话的活，比如出图出音频、格式冻结之后的批量关卡、调研、只读审计。没有人设，没有记忆，没有邮件，交回结构化结果后上下文直接销毁。
- **取消**：招人、辞退、履历、名册、点对点邮件。

### 3.2 状态放在盘上，由盒子持有
规格和冻结的判据、git（每件活一个提交）、任务清单（带验收检查）、只追加的活日志（盒子附上写操作台账和检查结果）、工程地图（盒子从工程自动生成）、决策记录。

prompt 里只放三样：索引、不变量、本单契约。具体内容一律按需去读。

### 3.3 冠军棘轮：保证进度只进不退（直接回应「白花」）
- **冠军**：盒子持有一个指针，指向「当前最好的可交付版本」。冠军必须通过全部回归，并且过过一次独立验收。模型改不了这个指针。
- **挑战者**：任何改动、包括推倒重来，都只能在分支上做。要替换冠军，必须通过冠军的全部回归，并且未满足判据更少，或者在盲评成对比较里胜出。
- 推倒重来不用问人，但冠军一直都在。探索分支有花费上限，超了自动放弃。
- **随时可停**：停下来交付的就是冠军，前面花的钱不会白费。

### 3.4 裁判归盒子
- **确定性优先**：`godot_check`、录制的输入回放（从开始玩到通关再重来）、软锁检测、帧率、调色板或网格这类可以量化的项。验收通过的那一刻，回放就固化成回归用例，只追加，模型删不掉。每次快照后盒子自动跑，不花 token。
- **主观项**：LLM 只做「新版是不是比冠军好」的盲评成对比较，多次采样、左右换位，不打绝对分。问题拆成可判断的小问题，比如「角色在背景上是否一眼可辨」。
- **收敛**：判据在一个阶段内冻结，新发现的问题进待办，不进当前门槛。每条判据的尝试次数有上限，用满就自动转为已知缺口。不收敛时盒子要求换方法，而不是再磨一轮。
- 证据按「判据 + 内容哈希」缓存，工程没变就不重复验。

### 3.5 人在信息量最大的时候介入，而且不阻塞
- **开局校准**，整局最值钱的一问：给 2–3 个便宜的风格或原型方向让用户挑；拿一张图让用户打分，把「8 分」换算成我们的刻度；确认范围。带默认值和超时，用户不回就按默认往下走。
- **放量闸**：一个房间完整达标之前，不开始「复制 N 份」。
- **主观判据不收敛时**：只通知，比如「按目前趋势到不了 8 分，已改用 A 方案继续」，不停工。
- 对「不要问我」的理解是「别因为等我而停下」，不是「什么都别告诉我」。

## 4. 四方的分歧和我的取舍

| 分歧 | 取舍 |
|---|---|
| 要不要保留制作人：信息流视角主张保留成事件驱动、上限 4 万；另外两方主张取消 | **取消。** 决定做什么由主建造者来，盒子负责调度、状态和裁判 |
| 用户闸门要不要阻塞：唱反调视角主张 G1/G2 阻塞；控制论视角主张不阻塞 | **不阻塞，带默认值和超时。** 用户明确说了不要等他 |
| 阶段由谁定：唱反调视角主张盒子定 G1/G2；控制论视角主张阶段就是一次冠军晋升 | **盒子只定不变量**（冠军、冻结判据、放量闸），阶段内容由模型定 |
| 新架构能省多少 | 四方估计在 0.8–1.5 亿之间，约为现在的 1/10。**这是推算，没有实测** |

## 5. 已做的①②怎么处理
- **①（队员上下文封顶、每单重开）方向对，参数太松。** 交接记录 6 万字太大，应改成 2–5k 加指向活日志的指针；16 万的上限太宽，应收到 6–8 万；制作人还没加上限。在新架构里它会被「每单从盘上重建」取代，过渡期可以收紧参数后留着。
- **②（评审直达作者）是过渡方案。** 它解决了中间转话，但转来转去的仍然是 LLM 的意见。在新架构里由「冠军棘轮 + 成对比较 + 判据级计数」取代。

## 6. 落地顺序（先建两种模式都受益的基础设施，再拿数据决定）
1. **P1 盒子基础设施**：回放回归器（固定物理步长和随机种子）、冠军指针（快照仓库里一个盒子独占的 ref）、证据缓存、活日志、工程地图。现有团队模式和单 agent 模式都能直接用上。
2. **P2 单写者模式**：在 `/goal` 基础上强化。主建造者、一次性工人（复用 `task`）、功能清单（每条带检查）、开局校准、放量闸、冠军棘轮。
3. **P3 主观裁判**：盲评成对比较加判据账本。
4. **P4 A/B**：同一句话分别跑新模式和 `/team`，比较总 token、到第一个可玩版本的时间、门禁通过率、用户来回次数。按数据决定 `/team` 是否降级成展示层（它的观赏性可能是产品卖点）。
