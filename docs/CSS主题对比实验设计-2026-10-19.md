# GDBox CSS 插件对比实验设计

> 状态：设计稿，未执行（2026-10-19）
> 被测对象：`resources/godot/addons/gdbox_css`（commit `ab135105`）
> 用途：决定这个插件是否按「Agent 的 UI 风格通道」接进 GDBox，还是退回成一个给人用的独立 addon

## 要回答的问题

**主问题：GDBox 的 Agent 做 Godot UI 风格时，有 CSS 插件能不能做得更好、更好改、不更贵？**

拆成三个子问题，对应定位里的三条理由：

| # | 问题 | 为什么问 |
|---|---|---|
| Q1 | 质量：悬停、按下、禁用、焦点这些状态覆盖全不全，几个界面是否统一，好不好看 | 手写 `.tres` 或逐节点覆盖时，状态最容易漏 |
| Q2 | 好不好改：换一次主色、圆角要动几处，有没有漏改；新界面能不能自动跟上 | CSS 的核心卖点是「改一处，全局生效」 |
| Q3 | 过程成本：工具调用次数、耗时、费用、报错、返工 | 插件不能让 Agent 更贵、更容易出错 |

附带观察 Q4：Agent 会不会用错插件（写不支持的属性、选择器，或者看不见导入警告）。这关系到接入时技能要写多细。

**这一轮不回答：**
- 人类开发者愿不愿意写 CSS。产品主体是 Agent，这个另议。
- 贴图边框（九宫格）。插件还不支持，只在 T5 记录 Agent 怎么处理。

## 载体

第一轮的教训是「载体偏差」：四个 Agent 都跑在 Claude Code 里，结论被载体带偏了。
所以这一轮用 **GDBox 自己的 Agent**：`gdbox ask "<任务>" --allow-write --json --project <夹具>`。

- `ask` 的工具范围固定为 `godot*`、工程文件读写、素材库、工程库，没有 shell。两组完全一样。
- 模型用 GDBox 当前配置的对话模型。可选：换一个更弱和一个更强的模型各补一条链，看收益是否依赖模型强弱。
- 不连编辑器，两组都用不了 `editor_*`。

## 分组

| 组 | 工程 | 任务提示里多出的那一句 |
|---|---|---|
| A 对照 | 夹具原样 | 「统一风格可以用 Godot 的 Theme 资源。」 |
| B 实验 | 夹具 + 已装好并启用 `addons/gdbox_css` | 「工程里装了 GDBox CSS，可以在 .css 文件里写主题，导入后就是 Theme；说明见 addons/gdbox_css/README.md。」 |

**两组都给一句提示，差别只在媒介。** 如果只给 B 组提示，测到的就是「有没有人提醒它用 Theme」，而不是 CSS 本身的作用。
B 组这句话相当于将来技能的一小部分。真技能会写得更细，所以 B 组的结果偏保守。

## 夹具工程 `ui-lab`

一个小游戏的三个界面，全是 Godot 默认外观，没有任何样式：

| 场景 | 内容 |
|---|---|
| `main_menu.tscn`（主场景） | 标题 Label；开始、继续（disabled，表示还没有存档）、设置、退出 四个 Button；版本号 Label |
| `hud.tscn` | 血条 ProgressBar、金币 Label、暂停 Button |
| `settings.tscn` | 两个音量 HSlider、全屏 CheckBox、语言 OptionButton、玩家名 LineEdit、返回 Button |

每个场景都能单独运行。夹具 `git init` 后做一次初始提交，用来量 diff。
另做一个变体 `ui-lab-themed`：同样的场景，但已经带一份 `theme.tres` 并设为项目主题，给 T4 用。

## 任务

两组的提示逐字相同，只差上面那一句。

| 任务 | 提示 | 起点 | 测什么 |
|---|---|---|---|
| T1 新做风格 | 「把三个界面做成统一的暗色科幻风：主色青色，按钮带圆角，有悬停、按下、禁用效果；用手柄或键盘导航时要看得出焦点在哪。做完截图给我看。」 | 干净夹具 | Q1、Q3 |
| T2 改风格 | 「主色从青色换成橙色，按钮圆角再大一点。」 | T1 的结果，新开一次 ask，不带历史 | Q2 |
| T3 加界面 | 「加一个确认退出的弹窗（标题、说明文字、确定和取消按钮），风格跟现有界面一致。」 | T2 的结果，新开一次 ask | Q2 |
| T4 已有主题 | 「按钮改成描边风格：透明底、青色描边。」 | `ui-lab-themed` | B 组会不会另起一套 CSS，和原主题打架 |
| T5 边界 | 「把按钮换成像素风的贴图边框。」 | 干净夹具 | 插件帮不上的地方 Agent 怎么处理（不计分） |

只测 T1 会漏掉最大的差别。T2、T3 才是「改一处全局生效、新界面自动继承」能不能兑现的地方。
T2、T3 故意不带历史，模拟的是隔天在另一次对话里改，也就是真实的用法。

## 规模与顺序

- T1 → T2 → T3 是一条链，每组跑 3 条链；T4 每组 3 次；T5 每组 1 次。合计 2 ×（9 + 3 + 1）= **26 次 ask**。
- 两组交替跑（A1、B1、A2、B2……），避免模型服务的时段波动全落在同一组。
- 每格只有 3 个样本，只能看出大差别。差别小于下面的判定线，就按「没差别」算。

## 隔离

- **经验库会串。** Agent 会把经验写进 `<userData>/experience/`（通用层），前一次学到的「这个工程用 CSS」会被后一次读到。
  所以每次 ask 前，都把这个目录还原到实验开始前的备份。工程层的 `.gdbox/experience/` 跟着夹具复制，本来就是隔离的。
- 每次都从夹具的干净提交复制一份新目录。跑完把整个目录归档，包括 `.gdbox/`、截图、`git diff`、ask 的 JSON 输出和 stderr 进度。
- 实验目录放在 `H:\UnrealAgent\_gdbox-lab\css-ab\`，和第一轮放在一起，不进仓库。

## 指标

全部在跑完后由脚本测量，不用 Agent 的自述。

测量脚本 `measure.gd` 的做法：无头加载每个界面并加进场景树，等一帧，遍历所有 Control，读它**实际生效**的主题条目（`get_theme_stylebox` 等）。
这样不管 A 组用的是 `.tres`、逐节点覆盖还是代码里 `_ready()` 现建，都能量到，对两组公平。

| 指标 | 怎么量 | 问题 |
|---|---|---|
| 完成 | 最后一次 `godot_check` 0 报错，三个界面都能加载 | Q1 |
| 状态覆盖 | 每个 Button 的 normal、hover、pressed、disabled、focus 五个 stylebox 里，和 Godot 默认主题不同、彼此又能区分开的有几个，取平均，满分 5 | Q1 |
| 一致性 | 全部 Button 生效的 normal stylebox 归一化后有几种（1 种最好）；Label 字色有几种 | Q1 |
| 主色到位率（T2） | 全部按钮的背景色或描边色，色相落在橙色区间的比例 | Q2 |
| 改动面（T2） | `git diff --stat` 统计的文件数和行数 | Q2 |
| 继承（T3） | 新弹窗按钮的生效样式和已有按钮是否一致；为弹窗新写了多少行样式 | Q2 |
| 过程 | 工具调用次数、耗时、token 和费用（看 GDBox 的用量记录）、`godot_check` 失败次数 | Q3 |
| 违规 | 手写 `uid://`、改 `.godot/`、`.tres` / `.tscn` 解析失败 | Q3 |
| 插件误用（仅 B 组） | 重导一次统计导入警告条数；Agent 有没有处理这些警告 | Q4 |
| 外观 | 每个界面截一张正常态，拼成匿名对比图（左右随机、去掉组别），由你盲评 1–5 分：好看、统一、符合要求 | Q1 |

外观只交给你盲评，不用模型打分。「像不像科幻风」这种判断模型不可靠，第一轮里看图模型连 32 像素小人的衣服颜色都说不全对。

## 判定线（跑之前定死，防止事后找理由）

**值** —— 下面四条同时满足，就按定位推进（改写接入任务卡片：按需安装、技能、接风格包、导出成 `.tres`）：

1. T2 的改动行数，B 组中位数 ≤ A 组的 1/3，且主色到位率 B 组不低于 A 组；
2. 状态覆盖 B 组平均比 A 组高 ≥ 1；
3. 盲评 B 组不输 A 组（平均分差 ≥ −0.3）；
4. 过程费用 B 组 ≤ A 组的 1.2 倍。

**不值** —— A 组在 T2 也只改一处（Agent 自己就会建一份 `theme.tres` 集中管理），而且状态覆盖差距 < 0.5。
说明 CSS 对 Agent 没有带来额外价值：搁置接入，插件只作为给人用的独立 addon，再单独评估要不要上架。

**半值** —— 质量赢了，但 B 组误用多（平均每次 ≥ 3 条警告没处理，或 T4 出现两套主题打架）。
先做技能、让 `godot_check` 回传 CSS 警告，再只跑一轮 B 组复测。

## 已知会影响结果的点

- ~~`godot_check` 不回传 CSS 导入警告~~：试跑里 B 组 Agent 说它从首次导入的输出里看到了 `HSlider:focus` 的警告，并自己改了写法。
  每次照样统计最终剩下的警告条数。
- B 组的提示只有一句，偏保守（见「分组」）。
- `ask` 没有 shell，两组都不能自己写 Python 加工脚本，和真实的 GDBox 对话一致。

## 成本

- 机器时间：「加二段跳」实测每次 40–70 秒。UI 任务估计每次 2–5 分钟，26 次合计 1–2 小时。
- 费用：取决于配置的模型。正式开跑前先单跑一次 A-T1 和一次 B-T1 实测费用，再乘以 26，报给你批准。
- 你要花的时间：确认模型、批准费用，最后盲评一次（T1、T3 的截图，约 15 分钟）。

## 执行步骤

1. 搭夹具 `ui-lab` 和 `ui-lab-themed`；写 `measure.gd` 和拼图脚本。先手工做两份样本（一份 CSS、一份 `.tres`）校准 `measure.gd`。
2. 构建 `packages/cli` 拿到 `gdbox`，跑 `gdbox doctor`；单跑 A-T1、B-T1 各一次，确认能写文件、能截图，量出时间和费用。**到这里停下，等你批准总费用。**
3. 交替跑完全部 26 次，每次跑前还原经验库。
4. 算指标，出匿名对比图，你来盲评。
5. 写结论：按判定线给出「值 / 不值 / 半值」，附每格数据和典型失败案例。

### 试跑后对设计的修改

- **两组提示都加一句「Godot 编辑器没有开，不用编辑器工具：直接改工程文件，用无头检查和截图验证。」**（`prompts/common.txt`）。
  B-T1-r1 是因为编辑器断连才停的，A-T1-r1 遇到同样的回包却继续了。这属于载体的随机性，与 CSS 无关。A-T1-r1 是在加这句之前跑的，只算试跑数据。
- **用量从 GDBox 日志里取。** `ask` 子任务的对话记录不落盘；日志里按时间窗统计 `mcp-` 开头的 session 的请求数、请求体字节和耗时。
  所以正式实验期间不能同时跑别的 CLI `ask`。
- **改动面只算人写的。** GDBox 的写文件工具会把整份文件改成 CRLF，统计时忽略行尾；Godot 导入时生成的 `.import`、`.uid` 和 `.gdbox/` 不算。
- **一致性按变体分组。** B 组故意把 Start 做成 `primary` 变体，这不算不一致；改为统计同一变体里有几种样式。
- **经验隔离只挪本次新增的条目。** 原设计是整目录还原，但通用经验目录下的 `.trail/` 是用户自己对话的原始记录，整目录还原会误删。

### 试跑看出的事

- **T1 区分不了两组。** 不用插件时，Agent 手写 `.tres` 也能一次做到满分覆盖。决定性的数据会出在 T2、T3、T4。
- **插件有一处缺口：** `HSlider` / `VSlider` 不在插件的类型表里，`HSlider:focus` 被判成「没有这个状态」。Agent 自己绕到了 `::focus`。
  正式开跑前应该修掉，否则 B 组每条链都要在这里多绕一次。
- 你自己在 GDBox 里开着一个工作室对话（多个队员同时在跑），和实验共用同一个订阅。正式跑时两边会互相拖慢。

### 正式实验的估算

剩下 25 次（已完成的 B-T1-r2 算作 B 组第 1 条链的 T1；A-T1-r1 要按新提示重跑）。按每次约 3–4 分钟、约 20 次模型请求估算，
合计 **1.5–2 小时、约 500 次模型请求**，全部走 ChatGPT 订阅额度。T2、T3 改的是现成工程，应该比 T1 短。

### 判定

| 条件 | A | B | 结果 |
|---|---|---|---|
| 1. T2 改动行 B ≤ A/3，且主色到位率 B ≥ A | 120 行；到位率 1.00 | 39 行；到位率 0.45（三条链分别 0.17、0.17、1.00） | **不满足**（行数刚好达标，到位率不达标） |
| 2. 状态覆盖 B − A ≥ 1 | 5.00 | 4.87 | **不满足**（两组都顶到天花板） |
| 3. 盲评 B − A ≥ −0.3 | — | — | 待评分（条件 1、2 已不满足，盲评改变不了结论） |
| 4. 过程成本 B ≤ A × 1.2 | 2.9 MB、15.7 次请求 | 2.6 MB、15.6 次请求 | 满足 |

主色到位率按事先登记的口径计算：normal 态按钮的背景或描边落在橙色区间的比例。分析脚本里还有一个「界面上所有鲜艳色」的口径，B 组是 0.89。
差别在于 B 组两条链在 T1 把普通按钮做成了深蓝灰底、只在主按钮和悬停态用强调色。到 T2 时 Agent 只改了 `--accent` 一个变量，深蓝灰没动。
A 组改 `.tres` 时把整套配色（含中性色）都换成了暖色。看截图，A 组「整体变橙」，B 组是「橙色强调 + 原来的冷色底」。
**B 组改的行少，一部分是因为它做的事也少。**

对照「不值」的条件：A 组在 T2 也是集中改一份主题文件（三次都没有新增逐节点覆盖，改动 90% 以上在 `neon_theme.tres` 里），状态覆盖差 0.13 < 0.5。**满足「不值」。**

### 结论：不值（按事先定的判定线）

在 GDBox 当前的 Agent 和模型（`gpt-6.1-sol`）上，CSS 插件没有带来可测的好处：
有一句「可以用 Theme 资源」的提示，Agent 自己就会建一份集中的 `.tres`，状态全覆盖、不逐节点覆盖、新界面自动继承，成本和 B 组持平。
CSS 唯一明确的优势是改动更短（T1 少一半、T2 少三分之二），这对人审 diff 有用，但这次衡量的是 Agent 的产出，不是人审的体验。

### 其他观察

- **T4 有一个风险：B 组三次都把工程的主题从 `theme.tres` 换成了新写的 `ui.css`。** 旧文件留在原地但不再生效，也没有告诉用户。
  在已有主题的工程里，这等于悄悄换了真相源；队友再改 `theme.tres` 不会有任何效果。A 组三次都是直接改 `theme.tres`。
- **T5（贴图边框）B 组处理得对：** 读了 README，知道 CSS 不支持背景图，改用原生 `StyleBoxTexture` 的 `.tres`，没有硬套 CSS。
- B 组最终的 CSS 导入警告全部是 0；Agent 写的 CSS 很地道：变量、变体、`::placeholder`、`::selection`、`-godot-icon-*` 都用上了。

### 这次没覆盖到的（结论的适用范围）

- 只测了一个模型，而且是强模型。弱模型手写 `.tres` 更容易出错，CSS 可能更有用；设计里那条可选的换模型链没有跑。
- B 组只有一句提示，没有技能。
- 每格 3 个样本。
- 盲评被削弱：B 组两条链的深蓝灰底色在 T3 截图里能认出组别。
